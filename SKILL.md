# Academic Defense PPT Skill

Produce technically accurate, readable academic-defense presentations. Select visual grammar from the actual source; do not impose a universal card template.

## Principles
1. Scientific topology, terminology, equations and evidence boundaries take priority.
2. Prefer editable vector graphics and native PowerPoint text/shapes. When source-matched fidelity calls for a distinctive icon that native shapes would distort, use a provenance-recorded, licensed SVG asset (with a high-resolution transparent raster fallback if the PowerPoint renderer cannot embed that SVG). Keep scientific nodes, edges, labels and annotations editable.
3. Preserve source composition, panel order, proportions, arrows, branches, operators and line grammar.
4. Do not invent layers, edges, node mappings, equations or downstream blocks unsupported by the source.
5. Split dense mechanisms before shrinking labels.
6. Shadows are off by default. Reproduce them only when visible in the selected source, using explicit source-specific shapes; never inherit the PowerPoint theme shadow.
7. Distinguish source-visible redraws, paper/code-grounded reconstructions and domain adaptations.

## Workflow

1. Identify the audience, scientific claim, source files, delivery medium and final size. For a journal figure, record its current author-guide URL and production limits before layout.
2. Write the DeckSpec/SlideSpecs for a talk and a FigureContract for each figure. Mark source-visible, paper-grounded, domain-adapted or data-driven evidence and list unresolved claims.
3. Build ScientificIR from the source: critical nodes and edges, equations, row-level data or image processing history. Stop if a required claim has no traceable support.
   For a node-link method figure, require a nonempty source-derived critical-route list before rendering. Check grouped states and every repeated member or head separately; the presence of a color somewhere in the figure does not prove every attention bundle contains that head.
   For a source-grounded method figure, write the source-derived critical-edge checklist independently of the drawing code. Include any handoff from prepared artifacts to their query-time or downstream consumers that the claim depends on; a route audit of only self-declared drawing edges cannot detect an omitted relation. Check the source figure/caption for visual structures that carry meaning (such as graph connectivity, nested communities or parallel aggregation), and represent these as editable schematic marks when warranted. See `docs/GRAPHRAG_FIGURE_TRIAL_LESSONS.md` for the bounded example.
4. Before drawing from an author PDF, extract a source-observed layout/style record:
   `python tools/extract_source_layout.py source.pdf --page 1 --output out/source_layout.json`.
   If the figure occupies only a crop, supply `--region X0 Y0 X1 Y1` in PDF points. Use the resulting panel markers, source rectangles, repeated alignment groups, interstitial bands, low-ink raster gutters, relative object coordinates, text/font tiers, stroke/fill palette, clip regions and image provenance as evidence for the FigureSpec. A missing panel marker means no confirmed panel split. Geometric enclosures and raster gutters are review-only candidates with confidence/provenance; do not promote them to panels without visual review. A raw PDF line is recorded only as a nonsemantic stroke-segment candidate until arrowhead, topology and caption evidence confirm a relation. See `specs/source_figure_layout.schema.json` and `docs/P1_01_SOURCE_LAYOUT_EVIDENCE_2026-11-14.md`.
   The unified `tools/reproduce_research_figure.py` pipeline also writes this record before conversion and embeds its hash and summary in the delivery manifest.
   Before using unlabeled/nested candidates in a FigureSpec, create a review template with `python tools/source_layout_review.py template out/source_layout.json --output out/source_layout_review.json`. A named human reviewer must explicitly accept/reject candidates with a rationale and source locator; assistant visual triage cannot approve a panel. Validate the record with `python tools/source_layout_review.py validate out/source_layout.json out/source_layout_review.json --output out/source_layout_review_audit.json`. Pass the validated file to the unified pipeline with `--source-layout-review`; only accepted facts are copied into the manifest. The source-route recommendation is advisory and never overrides the importer evidence or release gate.
   Choose a source-matched style and arrange the panels. Preserve scientific relationships when changing layout between presentation and publication profiles.
   When a user expects the visual grammar of a paper figure, inspect the actual figure image before drawing and record 5–7 visible SourceStyleSpec anchors (composition, operator shapes/colors, paths, repetition/depth, notation, type/line treatment). Compare the rendered preview against those anchors; terminology extracted from the paper text is insufficient evidence for a source-matched style. The Transformer Figure 1/2 trial in `docs/TRANSFORMER_FIGURE_TRIAL_LESSONS.md` demonstrates the difference. For high-fidelity source redraws, freeze a source-derived checklist before seeing the output, then judge the actual exported PDF/PNG against it. The checklist must name the relationships and visual marks that a plausible but incorrect redraw might omit. For machine-learning architecture, residual and contrastive-matrix figures, adapt the source-grammar presets in `specs/ml_source_grammar_patterns_v76.json`; they define required semantics and marks, not fixed layouts. See `docs/ML_PAPER_FIGURE_FIDELITY_TRIAL.md` for U-Net, ResNet and CLIP examples.
   For multi-operator graph figures, distinguish source-required dependencies from a convenient reading order. Do not connect flexible operators into a fixed pipeline unless the paper does. Compare each source panel with the final render for *states before and after transformation*, node/edge meaning, relative density and annotation placement; document material simplifications. If fidelity and projection readability conflict, produce separately identified source-composition and presentation versions. The Tree-KG trial in `docs/TREEKG_FIGURE_TRIAL_LESSONS.md` shows this failure and correction.
   For a cross-source engineering system diagram, record the technical source and visual reference separately. State the assumed mission/configuration, mark optional hardware, label distinct interface types and line-junction conventions, and do not transfer mission-specific parts or numbers merely because they appear in the visual reference. See `docs/SPACECRAFT_SYSTEM_DIAGRAM_TRIAL_LESSONS.md`.
5. Render SVG and editable PPTX from the FigureSpec; export PDF on the recorded PowerPoint host. Keep the raw data/image and transformation record with the output.
   For a never-before-used author PDF, first run `tools/figure_first_pass_gate.py` to freeze the source profile and perform structural and local visual-difference QA. Use `--auto-export` where LibreOffice is available or `--exported-pdf` to use a PowerPoint-rendered PDF. A `NEEDS_REVIEW` result blocks a high-fidelity claim. See `docs/FIRST_PASS_FIGURE_FIDELITY_GATE.md` for strict ellipse recognition, mathematical font/raster/clip risk checks and blind first-attempt benchmarking. The quality gate does not determine scientific topology; FigureContract/source-derived edges remain mandatory.
   When the author supplies an original **vector PDF** and exact source composition is the priority, an alternate path is `python tools/pdf_figure_import.py source.pdf editable.pptx --report import.json`. It preserves individually editable vector paths and text plus independent source images. Then run `python tools/audit_imported_pdf_figure.py source.pdf editable.pptx`; inspect the PowerPoint-exported PNG beside the original, particularly clip-dependent plots, custom math fonts, color/alpha, tiny labels and unusually thick strokes. Structural audit PASS does not establish visual fidelity; stop or manually rebuild affected panels when the side-by-side review fails. This alternate route does not make its PDF-derived objects into a semantic FigureSpec automatically.
   Before delivery to a Windows/Office 2016 user, run `python tools/audit_office2016_compat.py candidate.pptx --json office2016_preflight.json`. This conservative OOXML preflight flags SVG/WebP/video/3D media, OLE/ActiveX and external non-hyperlink relationships, and reports font families likely to substitute. Normalize known PDF font aliases to installed Windows families. The preflight is not runtime certification: open, save and export the actual deck in the target PowerPoint 2016 installation before claiming compatibility.
   For a fully logged single-entrypoint run from an original vector PDF,
   call python tools/reproduce_research_figure.py source.pdf --output outdir
   --mode import --render-host auto. With a source-grounded FigureSpec, use
   --mode figurespec --figure-spec figure_specs/path.json instead; this is a
   distinct evidence route and its scientific topology must be verified.
   For quantitative paper diagrams, freeze original tables/units/aggregation
   rules independently and validate actual native plotted coordinates,
   not merely text labels or raster similarity; see
   docs/MMGRAPH_F2_NUMERIC_AUDIT_2026-11-13.md. A mismatch in source graphic
   versus paper table must be reported, preserving a source-visible copy
   alongside any independently named data-corrected alternative. For Office
   2016 deliveries, also run the native Windows COM round-trip in
   windows/Test-PowerPoint2016RoundTrip.ps1; Linux/LibreOffice and OOXML
   preflight are not substitutes.
   For source-visible PDF imports, run tools/audit_text_geometry.py against
   the original PDF and candidate PPTX. Its source-aware collision check must
   report zero introduced text overlaps and zero newly introduced text
   overflow; source-authored overlap and source-crop clipping are recorded
   separately. Verify exact text codepoints and font mapping. An unmapped
   control/private-use glyph is a hard review blocker, not a guessed operator.
   See docs/P0_TEXT_GEOMETRY_AND_GLYPH_AUDIT_2026-11-13.md.
6. Run the schema, scientific, geometry, accessibility, cross-format and render-record checks named below. Resolve every machine-detectable failure before review.
   For node-link figures, audit line intersections with node interiors and text after rendering (`python tools/audit_figure_occlusion.py path/to/FigureSpec.json` is a preflight). Text-box-only overlap checks miss connectors that cross labels or pass through filled nodes. Inspect the actual PDF/PNG at delivery size and reroute any remaining ambiguous crossings.
   For a multi-figure deck, repeat structural and visual checks on the final combined PPTX/PDF: assembly can reintroduce theme effects or change rendering even when each source figure passed. In model-mechanism diagrams, trace residual paths, masked inputs and multi-input operators to their actual sources; a labeled box alone does not establish the dependency.
7. Inspect the actual projection or print size and obtain independent domain review with the 15-task benchmark. Treat any hard failure or missing review as a release stop; ship only a clearly labeled development example until the release gate passes.

## Scope

The presentation profile supports projected defense slides. The publication profile re-lays out the same science for a named journal's final dimensions; its automatic checks are a technical preflight. Evidence status describes how directly a source supports the figure, separately from the output profile. This skill does not certify journal acceptance or make unsupported statistical, biological or engineering claims.

## Profiles
- A: black-and-white academic framework, Times New Roman, thin strokes and restrained section boundaries.
- B: engineering system flow, Microsoft YaHei, muted pastel modules, feedback and state transitions.
- C: source-matched journal/network figure, paper-specific typography, graph nodes/edges, sensor waveforms, pooling geometry, readout and fusion layout.

## FigureSpec

The UCI Wine scatter and distribution examples test a second chemistry dataset using `specs/wine_charts_v76.json`, `python tools/build_wine_scatter.py` and `python tools/validate_wine_scatter.py`. Its source does not report physical units for the selected measurements; the numeric axes disclose this, and coded cultivars are not named varieties.

`tools/chart_data.py` loads both datasets with source hashes and row links. `tools/chart_contract.py` enforces sample size, source and derived fields, axis type/unit/domain/category coverage, zero policy and bootstrap definitions across both datasets; run `python tools/test_chart_contract.py` when changing either contract. Other chart renderers still need dataset-specific adaptation.

Canonical source is JSON under `figure_specs/`. Render SVG and editable native PowerPoint from the same FigureSpec. C01 primitives include text, rect, trapezoid, line, polyline, ellipse, sensor and graph. F07 also uses grid and stack_grid. FigureSpec also supports editable freeform polygons and rotated text for paper-specific silhouettes and spatial labels; compare these primitives in the exported PPTX/PDF, since an SVG preview can hide a PowerPoint geometry error. For ML method figures, call the parameterized native components in `tools/ml_figure_components.py` after checking the source grammar; see `docs/ML_COMPONENT_PRESETS.md` for ports, visual bounds, examples and limits. GAT and DETR cross-family trials in `docs/ML_CROSS_FAMILY_TRIAL_2026-11.md` show why visible group ports, per-head checks, arrowhead scale and rendered math labels matter. The component gallery tests parameterized drawing; the Wide Residual Networks Figure 1 trial tests reuse within the residual family. Neither establishes speed or accuracy on a frozen, independent paper set.

Before drawing, write a FigureContract with one defensible claim, output mode, evidence status and unverified items. Every FigureSpec element must have a stable ID, semantic role and evidence reference. EvidenceRecords include a local source file hash and a precise local locator; when the primary artwork is not stored locally, state that the hash covers the evidence ledger rather than the original artwork. Validate against `specs/figure_spec_v76.schema.json` and run `python tools/validate_scientific_ir.py`. For C01, declared critical relations must agree with visible connectors in both `specs/c01_expected_topology_v76.json` and `specs/c01_standalone_expected_topology_v76.json`.

For quantitative figures, define source file/hash, row unit, variable units, sample size, transformations, chart kind, numerical axis domains and zero policy, and the meaning of each statistic/interval before rendering. Declare every derived axis/group field with its unit, source columns and calculation rule. Specify model algorithm, data split, tie handling and compared feature sets as structured fields that the builder and validator both use; do not let a renderer invent predicted labels or summary measures. Disclose why a numerical axis excludes zero. Use `specs/iris_charts_v76.json` for scatter, distribution, point interval, confusion matrix, ablation and trend interval examples; run `python tools/build_quantitative_examples.py` and `python tools/validate_quantitative_examples.py`. Preserve row-level links for raw points and calculation links for summaries; check plotted coordinates and summary geometry against their source values. Separate coincident or closely spaced raw points with bounded display-only offsets, keep summary marks clear of them, and disclose offsets in the caption; never silently hide observations. A preview chart is not evidence for an unprovided statistical claim.

Each quantitative FigureSpec records a canonical SHA-256 of its complete ChartSpec. Keep the ChartSpec, source data and FigureSpec together; `validate_scientific_ir.py` checks the digest, the embedded chart definition and source metadata against that exact configuration. The FigureSpec schema requires quantitative data-lineage fields. The independent review template separately locks the raw ChartSpec file hash, so configuration edits require a fresh review.

For image panels, retain raw image hash and license, calibration, crop/stitch/LUT/intensity history, scale bar calculation, linked quantification and text descriptions. The CC0 cell example is built with `python tools/build_image_quant_example.py` and checked with `python tools/validate_image_quant_example.py`. A raster picture is permitted only for a disclosed source image, never as a flattened substitute for editable axes and annotations.
If a source-paper photo or result crop is embedded for local comparison, give it a separate `source_artwork_excerpt` evidence record with file hash, page/crop locator and rights status. Describe any annotations already inside that crop as raster; do not call them editable because the surrounding method diagram is native PowerPoint.

Run `python tools/check_scientific_accessibility.py` before review. This project preflight checks text at 4.5:1 and essential chart marks/lines against the white plotting area at 3:1, then generates grayscale and approximate color-vision previews. These thresholds draw on WCAG non-text contrast guidance but do not certify a PPT or journal figure as WCAG conformant; inspect the actual delivery size and adjacent backgrounds manually.

Use `presentation` for projection QA and `publication` only after checking the target journal's current final-size and file-format rules. Both modes use the same scientific relationships and source data. Record actual PDF renderer, canonical hashes of generation-pipeline sources, and manual final-size inspection separately from automated checks. See `docs/SCIENTIFIC_FIGURE_GAP_AND_UPGRADE_PLAN_2026.md`.
Run `python tools/validate_output_profiles.py` to enforce the declared presentation size and minimum text floor. The 9.5 pt floor is a preflight threshold, not proof of projected readability. Publication builds require a journal-specific target contract; see `specs/output_profiles_v76.json`.
For a concrete publication example, run `python tools/build_publication_example.py` after the Iris build, then validate `python tools/validate_publication_example.py`. Record the journal, main/extended/supplementary figure class, current author-guide check date, maximum height and preferred submission format before building; these rules differ by figure class. The Q03 Nature-size main-figure panel reuses the same source rows and bootstrap summaries while changing layout and type size; its caption is in `docs/Q03_NATURE_PUBLICATION_CAPTION.md`.
Before delivery, run `python tools/validate_render_record.py`, `python tools/validate_render_semantics.py`, and `python tools/validate_legacy_label_parity.py`. The first checks canonical SVG/PPTX payloads, the committed Windows PowerPoint PDF export attestation and embedded PDF font names against the requested family; the second compares rendered scientific labels across SVG, editable PPTX and PDF; the third checks the five migrated figures against committed pre-V7.6 labels with only the documented C01 publisher-source correction allowed. B01/F07 did not have committed PPTX at that baseline, so their current PPTX is compared against the historical FigureSpec. The historical check needs full Git history. Font-name checks cannot establish every glyph's appearance, so inspect the final-size output as well. Regenerate the export record only on the actual export host after running `tools/export_quantitative_pdf.ps1`.

For release evaluation, run `python tools/validate_research_benchmark.py` and apply the anchored six-dimension rubric and all hard failures in `specs/research_figure_benchmark_v76.json`. Every dimension must meet the stated score floor; no average score overrides a critical relation/value error, unclear source status, undisclosed image processing or unreadable content. Use `docs/SCIENTIFIC_FIGURE_V76_COMPLETION_AUDIT.md` to distinguish current machine evidence from still-missing human checks. Automatic checks are a preflight; record independent domain review separately.
Before naming a build stable, prepare an unfilled review file with `python tools/validate_release_readiness.py --prepare review.json`. Assign each of the 15 tasks to an independent reviewer whose declared expertise covers that task's benchmark discipline. Reviewers first inspect sources and figures without the benchmark expectations or implementation notes, recording task-level initial scores and evidence. They then inspect the specs and known traps, reconcile differences, and record source checks, six evidence-backed final scores, final-size inspection and hard failures. Run `python tools/validate_release_readiness.py --review review.json`; any missing review, mismatched reviewer field, changed SVG/PPTX/PDF/preview hash or hard failure blocks release. The gate verifies the review record, not the actual order of inspection. The in-memory tests in `tools/test_release_readiness.py` are synthetic and do not count as an actual review.
For a portable handoff, create two separate archives: `python tools/prepare_scientific_review_bundle.py --stage initial --output initial_review.zip` and `python tools/prepare_scientific_review_bundle.py --stage reconciliation --output reconciliation_review.zip`. Send the initial archive first and freeze each reviewer's scores and evidence before sending the reconciliation archive. The first contains only sources, figures and a neutral initial form. The second contains task inputs, builders, validators, expected findings, known traps and an unfilled JSON template; it can rebuild the quantitative figures and recheck canonical output hashes. File names and source documents may still disclose the project version. Neither archive asserts reviewer approval.

## Deck planning (V7.5 draft)
Before drawing, create a DeckSpec with audience, time budget, narrative order, delivery requirements and ordered SlideSpecs. Each SlideSpec needs one defensible claim, source evidence/status, page role, layout, on-slide text and speaker notes. Keep FigureSpec scientific topology independent of style and page layout. Derive a SourceStyleSpec from 5–7 evidenced visual anchors. Follow `docs/DECK_PLANNING_V75.md` and validate the example contract with `python tools/validate_deck_spec.py`.

## C01 source-matched pattern
FBG: sensor rows and waveforms → OCF/notch filter (operational component suppressed; subtle fault cues clearer) → band-pass filters → frequency-band subgraphs → connected total graph → SEANet input. Show inter-band links schematically when the exact adjacency is unavailable; do not depict a star aggregation as the graph topology.
SEANet: Input → first GCN → first pooling → second GCN → second pooling → upper SR → summation → Dense → fault class. Input also enters the energy-assist module, which feeds the first GCN; the first pooling branches to a lower SR that also feeds the summation. Do not draw an EA-to-lower-SR shortcut.
The paper text defines SR as sensitivity-aware readout. Sensor photographs may be replaced with vector silhouettes when vector-first output is required; disclose this. Graph coordinates remain schematic unless a numerical adjacency matrix is available.

## Composite defense-slide layout
When the user wants the complete method on one slide, use the V7.4 layout:
- Two related figure panels stacked in the left column.
- Reading guide, evidence boundary and citation in the right column.
- Reflow dense modules for the narrow panel; do not uniformly scale a full-width diagram.
- Keep the two-slide V7.3 version as the detail/teaching alternative.

## QA
Verify topology and terminology against the paper/caption/official code. Render the complete deck to PDF. Check text overlaps, line-through-node/text occlusion, clipping, out-of-bounds objects, SVG validity, raster objects and theme shadows. For a source-matched redraw, compare the final rendered image side by side with the cited source figure and record material visual differences and their scientific effect. Do not claim pixel identity without high-resolution source and direct overlay.
